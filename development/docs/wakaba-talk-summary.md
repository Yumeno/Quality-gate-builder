## 2. 中心となる問い

> 「ハルシネーションを減らすにはどうするか」ではなく、「品質とは何か」を問い直す。

「何をもって『完成した』と言うのか。コードか、実装の正確さか、ある状態が満たされていることなのか」という根本的な検討から、レイヤ別に検証責務を固定し複数視点から出力を判定する構造を設計する、というアプローチが提示される。

## 3. 用語・原則の前提整理

### 3.1 テストと品質の定義

- **テスト** (ISO/IEC/IEEE 29119-1:2022): リスクベースのアプローチの下で静的および動的技法を用い、ソフトウェアが仕様や要求事項を満たしていることを検証 (Verification) 妥当性確認 (Validation) する一連のプロセス
- **品質** (ISO 9000): 対象に本来備わっている特性の集まりが要求事項を満たす程度
- **品質** (ISO/IEC 25000:2014): 明示された条件下で使用するとき、明示的ニーズ又は暗黙のニーズを満たすためのソフトウェア製品の能力
- **結論**: 「品質」とは「要求を満たしていること」

### 3.2 高品質の定義

- 「定められた要求事項に対して要求を満たしていること。超過でも未満でもない」
- 超過もダメ、というのが忘れられがちな点として強調される
- 達成のためにはレイヤごとに要求を明確化しそれを達成する

### 3.3 単一責任原則・開放閉鎖原則のテストへの応用

- **テストにおける単一責任原則**: テストは単一のスコープについて責任を持ち、その検証・妥当性確認をカプセル化すべき
- **テストにおける開放閉鎖原則**: テスト内容は階層の追加に対しては開いており、修正に対しては閉じているべき

### 3.4 階層化自動テストの基本原則

- 境界付けられたコンテキストに応じてテストを分割する
- テストの関心事を見るべきものと完結できる単位で分割する
- テストで見るべきものをフローと状態に分割する
- 階層テストはそれぞれ独立して機能する
- 階層テストはプロセスに要求されるコンテキストの有無で増減する
- ツールの謳う使い方に囚われない

## 4. AI の本義

### 4.1 LLM 系生成 AI の位置づけ

- **意味的制約の中で「揺らぎ」を提供できること**
- AI は **決定装置ではなく探索装置**
- その価値は「ただ一つの答えを決めること」にはなく、「揺らぐ海の中から文脈に応じて異なる切片を引き上げられること」にある
- AI はインターネット上の知識や言説の分布を強く反映し、最大公約数に近い答えを返しやすい
- この性質によって AI の出力は一定の方向へ収束しているように見えるが、その収束は真理への到達を意味しない
- 学習された言説空間の中でもっとも選ばれやすい切片が浮かび上がっているにすぎない

### 4.2 AI 遣いに大切なこと

- 重要なのは **「決定を委ねること」ではない**
- AI が引き上げた切片をどう受け止めるかが重要
- 「どの制約で比較し、どの検査で退け、どの根拠で採用するのか」
- AI の出力したものは **「成果物」ではなく「候補」** でしかない
- 候補である以上、採用を考える必要がある
- 採用とは「定められた制約や基準の元、優劣を比較・検査し、根拠を持って採用を決心すること」

## 5. AI 利用で何が壊れるのか

### 5.1 保証の所在

- 壊れるのはコードだけではない
- 本当に壊れてしまうのは **「保証の所在」**
- 「xUnit やってるから保証できてるもん」は突っ込みどころに溢れるが、一般的にはこの延長でコードが保証していると考えられている
- 「コードがドキュメントである」も類例の一つ
- このコードがドキュメントには暗黙的に保証が含まれている

### 5.2 コードが暗黙的に保証していたもの

- ビジネスモデル・ルール
- 業務状態
- 受け入れ条件
- 安全境界
- UX
- 要求・制約・状態
- 判定基準

「これがあるので企画と開発が協働しやすい訳だが、ここに無制約の AI を導入すると暗黙の保証が破綻しはじめる」

「AI は既存のコードと同じ形で出力する保証はないので。そもそも、AI の本義は『釜で踊るうどん同様』『揺らぐことにこそに価値がある』」

「つまり大切なことは AI が『正しい』コードを書くかどうかにはない。大切なのは『何が変わってよくて何が変わってはいけないか』が定められていること」

## 6. 保証対象の転換

### 6.1 ボルトの例えによる説明

- ISO や JIS で定められた要求仕様に従って作られている大量生産品
- 我々はボルトの素体となる合金の組成を意識するか? — アルミや鉄などの大まかな材質の違いくらいしか意識しない
- 「我々が見出す価値は『何でどうやって作られているか』ではなく『何が出来るものなのか』なのです」
- 例: 「適正締付トルクに対してどれだけの適正締付軸力を得られるのか」

### 6.2 結論

- **「コードの同一性ではなく成立すべき状態を保証する」**
- 保証すべき成立状態: ビジネスモデル/ルール、業務状態、受け入れ条件、安全境界、UX、要求・制約・状態、判定基準
- 「ビジネスモデルから安全境界までが保証されているのならば全てを作り直してもよいのでは?」

## 7. 八百万と御柱

### 7.1 八百万 (Yaoyorozu)

- 原義: 数え切れないほど多くの神々・もの・働きが世界に宿るという考え方
- 重要: 単一の絶対者がすべてを決めるのではなく、多数の観点や働きが並び立つこと
- 「八百万は『多様な観点が同時に存在する世界観』」

実装としての Yaoyorozu:

- AI の出力、人間の判断、REQ、UI 契約、テスト、証跡、検証器など
- 多数の観点を集めひとつの実装を審議するための基盤
- AI の応答や人間の感想をそのまま正解にしない
- 正しさは「要求ごとに固定された契約」と「再実行可能な証跡」によって保証する
- **「揺らぎを否定する場所ではなく、揺らぎを審議可能な形に置く場所」**

### 7.2 御柱 (Mihashira)

- 原義: 神域や共同体に打ち立てられる柱、場の中心・境界・支えを示すもの
- 「三柱」として取ると、三つの柱あるいは三柱の神を数える言葉
- **三貴子判定核** として実装される（天照大御神・月読命・須佐之男）

実装としての mihashira:

- 三貴子判定核の実行入口
- 1 つの要求に対して UI 契約検証と L1 から L6 の階層化テストを実行
- 結果を ALLOW または DENY として判定
- 実行されたコマンドの終了コード、xUnit XML、UI 契約検証結果、gate JSON をログとして残す
- 判定は AI の返答でも人間の雰囲気でもコードの見た目でもない
- **「AI が出した候補を要求の証跡として採用してよいかを決める判定核」**

### 7.3 三者の役割整理

- **八百万**: 揺らぎ（多様な切片）を集め審議可能にする
- **御柱**: 揺らいではいけないものを固定する
- **Mihashira**: 固定された要求に対して通過判定を出す
- **「AI は候補を出す、御柱は通してよいかを決める」**
- この分担によって AI の揺らぎは統制された形で利用可能になる

## 8. 要求・UI 契約・証跡・判定核

### 8.1 要求 (REQ)

- **「何を満たすべきかを固定する単位」**
- 要求がなければ「何を比較し、何を検査し、何を根拠に採用するのか」を決められない
- 要求は **「見るべき階層を分ける」**

スライド上で示された L1〜L6 の概念定義:

- **L1: 処理保証** — 要求・制約・状態、判定基準を見る
- **L2: 状態生成保証** — 業務状態が正しく作られるかを見る
- **L3: 境界保証** — 安全境界と受け入れ条件を見る
- **L4: フロー保証** — ビジネスルールと処理順序を見る
- **L5: 表現保証** — UX と UI 契約を見る
- **L6: 体験保証** — 業務状態と画面遷移を見る

注記:

- L1〜L6 は偉さの定義やテストの種類ではない
- 保証したいものをどの階層で見るかを分けるための名前
- 要求が必要とする階層だけを判定すればよい
- これにより AI の出力を「なんとなくレビュー」せずに済む

**実装側 (`yaoyorozu-system/core`) では L1〜L6 が異なる定義（画面遷移/画面描画/コールツリー/HTTP 入力検証/アクション変数/処理入出力）になっており、スライドの概念ラベルと実装ラベルは一致していない**。この差は qgb 側で整理が必要（GitHub Issue で別途扱う）。

### 8.2 UI 契約

- ユーザーに見えるべきもの、操作できるべきもの、見えてはいけないものを固定する契約
- 見た目そのものを固定するものではない
- UI 契約が固定するのは見た目ではなく、**ユーザーが果たせること**
- 押せるべき操作があること、判断に必要な情報があること、見えてはいけない情報が見えないこと
- **「画面の見た目ではなく、体験の成立条件を固定する」**

### 8.3 証跡

- 要求を満たしていることを後から確認できる形で残したもの
- AI の出力はその場ではもっともらしく見える
- しかし、もっともらしさは採用の根拠にはならない
- 採用の根拠: 何を実行し、何が通り、何が落ち、どの要求を満たしたか
- 証跡があることで採用判断はその場の納得ではなく後から追える根拠になる
- 証跡があれば AI の揺らぎを履歴ではなく **判定対象** として扱える

証跡の種類:

- 終了コード — 実行結果が成功したかを示す
- xUnit XML — どのテストが通りどのテストが落ちたかを示す
- UI 契約検証結果 — 画面が体験の成立条件を満たしたかを示す
- gate JSON — 要求ごとの判定結果を機械が読める形で残す
- ログ — なぜその判定になったのかを人間が追える形で残す

「証跡とは AI が正しそうに見えた記録ではなく、要求に対して通してよいと判断しうる根拠」

### 8.4 判定核 (Mihashira)

- **「正しそうかどうか」を見ない**
- 判定核が見るもの:
  - 満たすべき要求があるか
  - 要求に対応する検査があるか
  - 検査結果が証跡として残っているか
  - 必要な階層が通っているか
- ALLOW または DENY を返す
- ALLOW: 要求に対して候補を採用してよいという判定
- DENY: 要求に対して候補を採用してはいけないという判定
- **DENY は失敗ではない** — AI の揺らぎを安全に受け止めた結果
- 落とせるから何度でも生成できる、通せるから根拠を持って採用できる
- 判定核があることで AI の出力は成果物ではなく候補として扱える

## 9. 不易と流行

- 生成 AI は現時点においてまだ「流行」の品
- 品質構造は世紀を超えてなお続く「不易」
- 流行を使うには「不易を外に出す」必要がある
- **コードは「流行」に近づく**
- **要求は「不易」に近づく**
- **UX も「不易」に近づく**
- **ビジネスモデルはさらに「不易」に近づく**
- AI 時代において「固定すべきもの」はコードではなくなる
- 固定すべきものは **「要求、制約、検査、証跡、判定」**

## 10. 結び

### 10.1 「コシ」を与える

- AI が揺らぐなら「揺らぎを止める」のではなく **「揺らぎを受け止める構造を作る」**
- それが「階層化品質設計」
- 「AI の揺らぎに『コシ』を与える」とは「揺らぎを消すこと」ではなく **「揺らいでも要求へ戻れる復元力を設計すること」**

### 10.2 AI 時代の品質保証

- AI は決定装置ではなく探索装置
- 品質とは要求を満たしていること
- AI に決定させることではなく **AI の候補を通す構造を設計すること**
- プロンプトではなく品質構造を持つ
- コードではなく保証したい状態を見る
- 組成ではなく何が実現できるのかを見る

## 12. qgb への影響

本トークの思想は、`requirements_and_development.md` v0.2 の以下の部分に直接的に対応する:

- §2.1 「LLM の出力や評価は確率的に揺れる。LLM の主観評価をそのまま品質保証の根拠とすることは危険」
- §3.2 「LLM 評価を単独の合格根拠にしない」「ALLOW は『定義済み検査に通過した』ことのみを意味する」
- §6.5 L1〜L6 の階層分け（ただし定義は wakaba 実装と異なる、要整理）
- §6.4 ALLOW / DENY / REVIEW の判定（wakaba 実装は ALLOW / DENY の 2 状態、REVIEW は qgb 独自拡張）
- §F-011 gate.json の構造
- C-001 「LLM 評価を単独の合格根拠にしない」

qgb は wakaba 氏の思想を出発点としつつ、対象言語・処理系を広げる方向で再構成する。具体的な相違点と整理方針は GitHub Issue (`spec-review` ラベル) で個別に扱う。
