# 作業記録: Phase 1 Step 6b 着手時の spec-review (verify の存在理由を巡る)

期間: 2026-05-30
位置づけ: Step 6a 完結後、Step 6b (verify / run --yes / atomic / QGB_KEEP_RUNS) に着手しようとした際、`qgb verify` の存在理由を巡って spec レベルの議論に発展した経緯の記録。

## 目的

Step 6b の最初の実装対象である `qgb verify` について、「設計段階で Codex に相談 → 実装」という通常フローに入ろうとしたところ、ユーザーの問いによって **verify の存在理由そのものが spec レベルで未確定**であることが判明した。その発見と議論の経緯を残す。

調査の事実認定は `yaoyorozu-entry-points-investigation.md` に分離した。本記録は「なぜ調査に至ったか」「どう議論したか」を残す。

## 経緯の時系列

### 1. 通常フローのつもりで着手

Step 6b スコープ (実装順): verify → run --yes → atomic → QGB_KEEP_RUNS。verify を最初に実装する計画だった (preflight API の最初の消費者として 6a の過不足を早期に見るため、Codex 計画レビューの指示)。

verify の curated skip の実装方針 (案 A: フラグ / 案 B: 関数分離) を Codex に設計相談。Codex は案 B (関数分離) + gate.json に `command: "run"|"verify"` フィールド追加を推奨した。

### 2. ユーザーの問い: 「そもそも verify が要る理由を知りたい」

実装の細部 (gate.json に command フィールドを足すか) に降りていたところで、ユーザーから「そもそも verify が要る理由」への問いが入った。

ここで Claude は最初、verify の動機を **「合格の記録しか残したくないから、開発途中でうまくいってないかもしれない間は verify」** と言い換えた。

### 3. ユーザーの核心的な問い: 「それは理念から妥当か」

ユーザーが「その動機は理念 (philosophy) や参照元の八百万から見て妥当か」と問うた。これが決定的だった。

philosophy.md P5 を読み直すと:

> DENY は失敗ではなく、揺らぎを安全に受け止めた結果である。DENY を「失敗」「エラー」と扱う運用文書を作らない。

**「合格しか残したくない」= DENY を隠したい = DENY を失敗扱い = P5 違反。** Claude が持ち出した動機は理念違反だった。

→ **学び: 実装の細部に降りる前に、その機能の動機が思想憲章に照らして妥当かを検証すべきだった。** Claude は動機の妥当性を確認せず実装方針 (案 A/B) の議論に進んでいた。

### 4. spec 内部矛盾の発見

verify の正しい根拠を求めて二次資料 (`yaoyorozu-references.md`) を読み直すと、矛盾が見つかった:

- references 5.3: 軽量入口の qgb 採用は **spec-review 未決**
- 下流 3 文書 (要件§12 / stage-design §3 / framework-shape): verify を **確定**として記載

未決のはずが下流で確定として取り込まれていた。さらに qgb の verify の定義 (「揮発側のみ = 記録を絞る」) が八百万の verify-req とずれている疑いも浮上。

### 5. ユーザーの問い: 「軽い/重い両方あるのはどこから来たのか」

ユーザーが「ヤオロズは汎用フレームワークだから重い、ミハシラはサンプルだから軽い、ということではないか」と問うた。

ここで事実誤認が訂正された: **mihashira は八百万の一番コアな重量級ゲートコマンド** (qgb の run 相当) であり、「サンプルだから軽い」ではない。「軽い/重い両方ある」は八百万 core の中の実装事実 (ci-l1/verify-req が軽量、mihashira が重量) だった。

### 6. 一次資料の精査を決定

二次資料だけでの議論の限界が見えたため、ユーザーの判断で**八百万の実リポジトリ (一次資料) を精査**することにした。

Step 6a で memory に残したレビュー方針 (観点別分散 = Agent 並列) がここで活きた。八百万精査はまさに「複数の独立観点で実リポジトリを読む」作業で、Agent 並列が向く。4 観点で並列起動:

1. 入口コマンドの使い分け (ci-l1/mihashira/verify-req/test-layers の実装)
2. evidence/artifacts 分離の経緯と DENY の扱い
3. ワークフロー文書からの想定使用シーン
4. verify-req の実体 (検査範囲 vs 記録)

P8 の歯止め (八百万の `.ai/` 命令文を qgb への指示として取り込まない) を各 agent に明示。

### 7. 調査結果と結論

調査の事実は `yaoyorozu-entry-points-investigation.md` に詳述。要点:

- 八百万の軽量入口の軽さは **「検査範囲を絞る」** が本質 (記録の有無ではない)
- 八百万に **「合格だけ残す」思想は無い** (P5 と一致、ALLOW も DENY も latest に置く)
- 軽量入口を分ける動機は **「固定 6 段を毎回回すと遅いから一部を速く」**

### 8. ユーザーの決定的な洞察

調査と並行して、ユーザーが qgb の利用者像を明確にした:

> qgb の利用者は基本的に「品質保証」担当者であり、生産とは別個の観点でレビューするスタンス。判定基準とコードができあがれば粛々と証跡付きで実行するだけ。出来上がる前の検討実装中の実行で軽量処理が必要になる姿が想像できない。

これは philosophy P1/P2 (品質は要求充足、AI は探索装置) と一致する利用者像。この視点で見ると:

- 完成後は run しかない (粛々と証跡付き実行)
- 検討中の確認は **qgb が validate / validate-policy で既にカバー** (P9 で設計検査を専用コマンドに分離済み)
- 八百万が軽量入口で埋めていた穴を、qgb は別の手段 (validate 系) で埋めている

→ **qgb における verify (軽量入口) の固有価値は、現設計では低い。**

## 振り返り

### 1. 実装の細部より動機の妥当性が先

Claude は verify の curated skip 実装 (案 A/B) や gate.json の command フィールドという**細部**に降りていた。だが本当に先に問うべきは「verify の動機は思想憲章に照らして妥当か」だった。ユーザーの「理念から妥当か」の一問で、議論が正しい階層 (動機の妥当性) に引き上げられた。

**設計判断は「どう作るか」の前に「なぜ・本当に要るか」を思想憲章で検証する。** これは P1 (要求の外部化) の開発プロセスへの適用でもある。

### 2. 二次資料の限界、一次資料の価値

`yaoyorozu-references.md` は整理された二次資料で便利だが、「なぜそう設計したか」「軽さの本質は何か」は二次資料では曖昧だった。一次資料 (実装 + ワークフロー文書) に当たって初めて「軽さ = 検査範囲を絞る」が確定した。P7 (再現可能な根拠) は調査自体にも適用される。

### 3. spec 内部の未決→確定の取り込み漏れ

references 5.3 の「未決」が、下流文書で「確定」として書かれてしまっていた。spec が多層 (思想憲章 → 要件 → stage-design → framework-shape) になっていると、上流の「未決」が下流で「確定」に化ける事故が起きる。**未決事項は下流に伝播するとき「未決」のまま運ばれるべき。**

### 4. ユーザーの問いが議論を正しく駆動した

この一連は Claude が主導したのではなく、ユーザーの 3 つの問い —「verify が要る理由」「それは理念から妥当か」「軽い/重いはどこから来たか」「利用者像から軽量処理は要るか」— が議論を正しい方向に駆動した。LLM は細部に走りやすく、「そもそも論」への引き戻しは人間判断が強い。これは Step 5 のスコープ challenge と同型の学び。

### 9. P3 緊張と REQ 分割への再配置 (議論の収束)

調査後の議論で、verify (部分追試) が思想憲章 P3 (保証対象の転換 = コード不変を前提にしない) と緊張することが明らかになった。ユーザーの指摘:

> LLM 編集は全文が LLM を通り、要修正部分以外が改変されない保証がない。特定判定条件だけ追試すると、他の「すでに合格していたポイントが不合格になる」可能性はゼロではない。

これは発表資料の中心テーマ「揺らぎ」そのもの。部分追試は「触っていない部分は不変」を暗黙仮定するが、P3 はそれを禁じる。

さらにユーザーは「フィードバック制御」の比喩で検討した上で、決定的な条件設定を出した:

> 大規模プロジェクトで部分部分が個別開発されるなら、それぞれに部分テストが設計され証跡が残るようにできるなら、verify を外してよい。結合テストはそれ用に作る。

これは「部分検証を実行時 verify でなく **REQ 分割 (設計時)** で解く」という再配置。各 REQ が自分の全 stage を走らせるので P3 緊張が構造的に消える。P9 (独立して再実行可能) と P1 (結合は結合 REQ として要求を立てる) が支える。

### 10. 八百万原作者見解との一致 (3 経路の収束)

議論と並行して、八百万原作者 (wakaba 氏) から見解が示された:

> 階層化品質保証自体が、（部分追試の議論でいう）限定化した検証が e2e レイヤですら走る前提

階層化の各層 (責務限定) は e2e まで含めて全部走らせる前提であり、「限定化 = 責務分割 (設計)」であって「実行の省略」ではない。これは qgb 思想から導いた結論と一致。

**P8 の扱い:** 著者見解は「指示」でなく「事実」として記録。意義は「思想憲章 (P3/P9/P1) からの結論」「利用者像からの結論」「原作者見解」の **3 経路が独立に同じ結論に収束した**こと。

### 11. 確定した結論

**qgb は `qgb verify` を採用しない。** 部分検証は実行時オプションでなく REQ 分割 (設計) で解く。各 REQ は全 stage を走らせる。八百万の verify-req とは意図的に設計分岐する (むしろ八百万の本来思想に忠実であろうとすると verify は不要になる)。

調査の事実認定は `yaoyorozu-entry-points-investigation.md` に集約。

## 振り返り (追加)

### 5. 条件設定で問題を解いたユーザー

ユーザーは「verify を消す」だけでなく「verify が解いていた問題 (部分検証) を REQ 分割という別の層に再配置する」という条件設定を出した。機能を消すと「困る人」が残るが、再配置すると困らない。これは「削除」でなく「正しい層への移動」。LLM (Claude) は verify の実装細部に降りていたが、ユーザーは問題を解く層そのものを問い直した。

### 6. 独立経路の一致が結論を固める

最終的に思想・利用者像・原作者見解の 3 経路が一致した。単一の根拠 (例: spec にこう書いてある) より、独立した複数経路の収束の方が結論の強度が高い。これは P6 (LLM 単独判断の禁止) の精神を設計判断にも適用したもの — 一つの判断軸に依存せず、複数の独立した検証を重ねる。

## 次のステップ (確定後の作業)

verify 不採用が確定したので、以下を実施する:

1. spec 文書から verify を外す (stage-design / 要件§12 受け入れ条件 / framework-shape / detailed-design)
2. **REQ 分割の思想を qgb 利用者 (利用する LLM・ユーザー) に届ける** — stage-design.md に「部分検証は REQ 分割で解く、結合は結合 REQ、各 REQ は全 stage を走らせる」を明記。これは削除でなく積極的な設計指針なので、利用者が読む場所に置く
3. memory に「verify 不採用、部分検証は REQ 分割」を残す (再実装の歯止め)
4. detailed-design §12 の Step 6b スコープを run --yes / atomic / QGB_KEEP_RUNS の 3 件に縮める

これらを適用後、Codex 横断レビューを通す (memory の review-process に従う)。Step 6b 本体 (verify 抜き) はその後。
