# オーケストレーション設計ノート: 消費コンテキスト最適化とガチャの経済学

- 記録日: 2026-07-04
- 由来: 5.d canary 準備中の user 提起「ローコスト監査のループで品質は担保できるが、手戻りで結局コンテキストと時間を食う。消費コンテキストの最適化にはタスクごとの最適点があり、『ローコストモデル 100 体でガチャ』が必ずしも正解ではない」
- 実証基盤: Phase 5 (2026-06-28〜07-04) の実測。Fable 5 指揮 + sonnet 実装 + Codex 横断 + CI 実機の多層編成

## 0. 統べる思想: 至高は「一発」、以下は全て次善策 (user 明示 2026-07-04)

> 「十二分なコンテキストを用意して、そのコンテキストを不足なく理解できるモデルで 1 発で決める」が至高。それができないタスクに対してどうするか、が本ノートの主題。

- ループ・多層監査・多エージェントは目的ではなく、**一発が成立しない条件 (コンテキスト上限 / モデル能力 / 分業の必要) への補償**。手戻りとはまさに「一発できなかったことの代金」
- したがって編成設計の第一手は「エージェントを増やす」ではなく「**タスクを一発可能に近づける**」— コンテキストの精選と作り込み (本 repo の journal 文化・prejournal・compact 跨ぎ受け渡しはこの実践: セッションやモデルを跨いでも一発に近い立ち上がりを作る装置)
- ただし完全な一発が成立する理想世界でも、**検証の第二機能 = 証跡化 (P7) は消えない**。多層検証には (a) 誤り訂正 と (b) 監査可能な証拠づくり の 2 機能があり、(a) は一発の達成度に応じて削れるが、(b) は「全部理解して正しくやった」という主張こそ自己証明できない (P6) 以上、常に残る。qgb が守るのは (b) である

## 1. 中心命題 (次善策の経済学): ガチャの正否は検証コストで決まる

「弱いモデル多数で候補を量産し选別する」戦略 (ガチャ) が成立する条件は、**検証がほぼ無料であること**。SD 画像生成でガチャが正解なのは、100 枚出して一瞥する目視 1 秒が高精度判定器だから。コード・設計では候補の検証 (レビュー・テスト) が生成より高価になり得るため、経済が逆転する。しかも失敗候補の棄却作業は指揮官 (orchestrator) のコンテキストに課税される。

> **生成の揺らぎを増やしてよいのは、検証を安くした後だけ。**

これは qgb 憲章 P5「落とせるから何度でも生成できる」と同根 — 機械ゲートの存在がガチャの免許証であり、**qgb はガチャの経済を成立させる検証インフラ**である。オーケストレーション設計論と qgb の理念は同じ場所に根を持つ。

## 2. 実測から出た編成原則 (Phase 5 の実データ)

1. **同種チェッカーの限界効用は急減する**: Codex 机上レビュー 6 巡 (finding 系列 5→5→4→1→2→2、収束せず) より実機 fixture 1 巡が多くの欠陥を捕捉 (5.a-2-4)。同種監査は盲点が相関し、2 巡目以降の発見が薄い
2. **数より多様性**: 5 レンズ (sonnet 並列) / Codex 横断 / CI 実機は互いに別クラスの欠陥を捕った — レンズ = 観点内の穴、Codex = レンズ間の隙間 (write 防御 vs delete 無防備)、CI = 全 reviewer が見逃した Python 3.13-only API (5.b 段階 5)。監査を足すなら同種 N でなく異種を
3. **手戻り単価は検出位置で桁が変わる**: 同一欠陥でも lint 時点 = 数行 fix、golden 生成後 = 再生成込み、リリース後 = 新バージョン。shift-left (実機 fixture 先行、書いた直後の lint) は「巡回数を増やす」でなく「1 巡の単価を下げる」施策
4. **集約は指揮官のコンテキストに課税される**: 各レンズに自己反証を義務付け (候補 7 → 報告 2 まで checker 側で削減)、調停コストを checker 側へ移転した。ローコスト監査 N 体の false positive を指揮官が捌く構図は、節約分を最も高価な場所に付け替えているだけ
5. **直列の強い 1 体 vs 並列の弱い N 体**: 状態依存・経路依存の作業 (本体実装・設計対話) は強い直列、無状態で分割可能な作業 (探索・観点別レビュー・横展開) は多様な並列 (既存 memory parallel-strategy と整合)

## 3. タスクごとの最適点を決める 3 変数

| 変数 | ガチャ側に振れる条件 | 強い少数側に振れる条件 |
|---|---|---|
| 検証可能性 | 機械検証が確立 (golden / 決定性 / lint) | 判断タスク (憲章の文言、設計分岐) |
| 逸脱の単価 | 可逆・内部物 (journal typo) | 不可逆・出荷物 (リリース、憲章) |
| プロジェクト段階 | 仕様凍結後・gate 確立後 | 仕様流動期 (何が当たりか未定義なガチャは当たり判定のないガチャ) |

**最適点は静的でない**: 検証系が整うほどガチャ側に動く。品質ゲートを先に立てる理由はここにもある。

## 4. モデル配役 (P9 の編成への適用)

2026-07-04 時点の想定: Fable 5 = 設計・憲章・指揮・検収 / Sonnet = 実装・skill 運転 (利用者代表性 + 系統分離) / Codex = 横断監査 (異系統レンズ) / Haiku = 記事・要約 (journal という豊富な原材料の圧縮再構成)。**モデルにも段階の単一責任 (P9) を適用した編成**。ただし理念の本論の執筆は圧縮でなく思想の文章なので上位モデルまたは人間の筆 (Haiku の適用限界)。

配役の系統分離は P12 (評価主体の独立性) の実装でもある: 作成者 (Fable 5) と運転者 (Sonnet) と監査者 (Codex) の系統を分けることで盲点の相関を下げる。canary #1 (2026-07-04) で「Fable 5 設営 → Fable 5 受験」が即座に見抜かれた実例は、系統共有の盲点/直感の共有を示す実測。
