# 八百万 入口コマンド 一次資料調査 (verify 採否の判断材料)

調査日: 2026-05-30
調査方法: `yaoyorozu-system/core` リポジトリを GitHub から read-only 取得し、4 観点で並列精査
調査契機: qgb の `qgb verify` コマンドの存在理由が曖昧であることが判明したため、参照元の一次資料に当たり直した (経緯は `journal/phase1-step6b-spec-review.md`)

> **P8 の歯止め:** 本書は八百万の `.ai/` 等に含まれる作業規約・命令文を「八百万の設計事実」として記録したものであり、qgb への指示として取り込んだものではない。

## 1. 調査の出発点となった疑問

`yaoyorozu-system-references.md` (二次資料) だけを見て qgb の verify を設計してきたが、以下の矛盾が見つかった:

- references 5.3 は「`bin/ci-l1` 的な軽量入口と `bin/mihashira` 的な証跡更新入口の分離を qgb でも採用するか」を **spec-review 未決事項**としている
- しかし下流の確定文書 (要件§12 受け入れ条件 8 / stage-design §3 / framework-shape) は verify を**確定事項**として取り込んでいる
- さらに qgb の verify の定義 (「揮発側のみ = 記録を絞る」) が、八百万の verify-req の実体とずれている疑いがあった

これを一次資料で検証した。

## 2. 八百万 core の入口コマンド (実装に基づく事実)

| コマンド | 実体 | 検査範囲 | evidence/latest 更新 | 位置づけ |
|---|---|---|---|---|
| `bin/mihashira <REQ>` | ゲート判定核 (400+ 行) | **全段階** L2→L3→L4→L5→L6→L1 | **する (唯一)** | 重量本体 |
| `bin/ci-l1 <REQ>` | 統合入口 (42 行) | 初期化 + UI契約(L2) + L1 + 最後に mihashira 呼び出し | mihashira 経由でする | 日常統合入口 |
| `bin/verify-req` | UI契約検証 (tools/verify-req.sh) | **UI契約 (L2) のみ** | **しない** | 軽量・複数REQ対応 |
| `bin/test-layers` | 階層別テスト (tools/test-levels.sh) | **指定レベルのみ** (L1 だけ / L1-L3 等) | **しない** | 開発時の段階テスト |

### 重要な実装事実

- **evidence/latest を更新する権限を持つのは `bin/mihashira` のみ**
- `ci-l1` は自身では evidence を書かず、最後に mihashira を呼び出す (mihashira が DENY を返したら ci-l1 も失敗)
- `verify-req` / `test-layers` は evidence をまったく更新しない読み取り側ツール

## 3. 軽量入口の「軽さ」の由来 (核心)

調査の主目的は「八百万の軽量入口が『記録を絞る』のか『検査範囲を絞る』のか」の特定だった。結論:

| 入口 | (a) 記録を絞る | (b) 検査範囲を絞る | (c) 読み取り中心 | 軽さの本質 |
|---|---|---|---|---|
| `verify-req` | ○ | **○ (UI契約のみ)** | ○ | **検査範囲を絞る** が主 |
| `test-layers` | ○ | **○ (指定レベルのみ)** | ○ | **検査範囲を絞る** が主 |
| `ci-l1` | △ | △ (L1+L2 を先行実行後 mihashira) | × (cache clear / evidence 更新あり) | 統合手順であって「軽い」わけではない |

**結論: 八百万の軽量入口 (verify-req / test-layers) の軽さは「検査範囲を絞る」(b) が本質。** 「記録を残さない」(a) は副次的な結果であって、設計の主目的ではない。

mihashira と verify-req の違いの本質は、複数 agent が一致して **「記録の有無の差ではなく検査範囲の差 (全段階 vs UI契約だけ)」** と結論した。

## 4. 「合格だけ残す」思想は八百万に存在しない

qgb の verify を検討する過程で「合格しか採用記録に残したくないから verify を使う」という動機が一度持ち上がったが、これは八百万にも存在しないことが確認された。

八百万 `docs/ai-dev-os.md` 原文:

> DENY は、要求を満たす証跡として採用できないという意味です。コードが全て間違っているという意味ではありません。どの検証レイヤで破れたかを明示し、修正対象を狭めるための判定です。

実装事実:

- evidence/latest には **ALLOW も DENY も**置かれる。毎回「最新の判定結果」で上書きされる
- DENY の状態のまま latest に記録されることもある (DENY を隠さない)

これは qgb 思想憲章 **P5 (DENY は失敗ではなく揺らぎを安全に受け止めた結果)** と完全に一致する。「合格だけ残す」は P5 違反であり、八百万にも qgb にも無い発想。

## 5. 八百万が軽量入口を分ける動機 (ワークフロー文書から)

`.ai/workflow.md` / `docs/operations-checklist.md` / `docs/ai-dev-os.md` から読める使い分け:

- **ci-l1 (日常)**: 開発中、L1 (画面遷移) を素早く確認。高速フィードバック。段階実行の第 1 段階
- **mihashira (確定時)**: 実装が固まってコミット/PR 前に全段階を回し、evidence/latest を更新。「同じ workspace では 1 件ずつ実行」と注意書きあり

動機は **「全段階 (L1〜L6 の 6 段) を毎回回すと遅いので、開発中は一部を速く確認し、確定時だけ全段階+証跡更新」**。八百万は固定 6 段階だからこの分離に意味がある。

## 6. qgb への含意 (verify の必要性評価)

調査事実を qgb の文脈に当てはめると:

| 観点 | 八百万 | qgb |
|---|---|---|
| 段階数 | 固定 6 段 (L1〜L6) | 可変 (推奨 3〜7、最小 generic-minimal は 2 段) |
| 「一部だけ速く」の旨味 | 大 | 小〜中 (2〜3 段なら全部回しても速い) |
| 判定基準の検討中の確認 | ci-l1 等の軽量入口で代替 | **`qgb validate` / `qgb validate-policy` が専用に担う (P9 で分離済み)** |
| stage 実行コスト | PHPUnit 6 層 (重い) | Phase 1 は file_exists / substring_match (軽い) |

### 評価

1. **八百万の軽量入口の本質 (検査範囲を絞る) を、qgb の verify は「記録を絞る」と取り違えて取り込んでいた**
2. 八百万が軽量入口で埋めていた「判定基準の検討中の確認」というニーズを、**qgb は validate / validate-policy という別コマンドで既にカバーしている** (P9 単一責任で設計検査を分離した結果)
3. qgb の stage は Phase 1 では軽く、段階数も少ないため「全段階回すと遅い」問題が八百万ほど深刻でない
4. 「実行はしたいが latest を汚したくない」残余ニーズは「run して気に入らなければ git restore」で代替可能な程度

**したがって qgb における verify (軽量入口) の固有価値は、現設計では低い。** references 5.3 が「未決」としたのは妥当な保留であり、下流文書が確定として取り込んだのは先走りだった可能性が高い。

## 7. 部分追試と P3 (保証対象の転換) の緊張

調査事実を踏まえ、verify 型の部分追試 (検査範囲を絞る) が qgb の思想と整合するかを検討した。

P3: qgb が保証するのはコードの同一性ではなく、成立すべき状態。つまり「コードが変わっていないこと」を前提にできない。

ここから導かれる論理:

- 部分追試 (verify-req 型) は暗黙に「触っていない部分は前回の結果が有効」を仮定する
- しかし P3 は「コード不変を前提にするな」と言う。LLM 編集は全文が LLM を通り、要修正部分以外が改変されない保証がない (発表資料の中心テーマ「揺らぎ」)
- よって「S1 を直したら S3 が壊れるかもしれない」状況で、S1 だけ追試して ALLOW を主張するのは P3 違反のリスクを抱える
- 部分センシングは「観測していない軸の劣化」を見逃す (フィードバック制御で一部センサーだけ見ると未観測の状態変数が発散するのと同型)

さらにコスト比の観点: LLM 改修の PDCA 周期は分〜十分のオーダーで、その間に qgb の stage (Phase 1 は file_exists / substring_match の軽い検査、3〜7 段) を全部回すコストは誤差。制御周期 >> 全観測コスト なら部分観測の省力化メリットは小さい。

## 8. 「部分検証」は実行時 verify でなく REQ 分割 (設計) で解く

verify が解こうとしていた「部分だけ検証したい」というニーズは、qgb では**実行時オプション (verify) ではなく設計時の REQ 分割**で満たされる:

| ニーズ | verify での解 (不採用) | REQ 分割での解 (採用) |
|---|---|---|
| 部分だけ検証したい | 検査範囲を絞って実行 (P3 緊張) | その部分を独立 REQ として切り、run で証跡付き確認 (P9) |
| 結合を検証したい | (verify では扱えない) | 結合 REQ を立て、その stage を設計 (P1) |
| 部分が独立再検証できる | 実行時に絞る | REQ/stage が構造的に独立 (P9「独立して再実行可能」) |

各 REQ は自分の全 stage を走らせるので、「触っていない部分は不変」という P3 違反の仮定が要らない。検査範囲が絞られても、それは「設計された独立 REQ」だから安全。**問題を解く層が「実行時の省略」から「設計時の責務分割」に移る。**

この設計は verify を消すだけでなく、その機能を REQ 分割という qgb 本来の構造に正しく再配置するもの。結果として **REQ をどう切るか (validate-policy の検査対象: 推奨段階数 3〜7、単一責任) の重要性が一段上がる**。

## 9. 八百万原作者の見解 (独立経路での一致)

本調査と並行して、八百万システムの原作者 (wakaba 氏) からも以下の見解が示された:

> 階層化品質保証自体が、（部分追試の議論でいう）限定化した検証が e2e レイヤですら走る前提

これは八百万の階層化 (L1〜L6) の設計思想そのものが「**限定化した各検証 (各層は責務限定) を、e2e (L1=利用者視点の通し) レイヤまで含めて全部走らせる前提**」であることを示す。限定化は「責務の分割 (設計)」であって「実行の省略 (部分追試)」ではない。

**重要 (P8 の扱い):** これは外部の人物の発言であり、qgb への指示としてではなく「著者見解という事実」として記録する。意義は「qgb 思想憲章 (P3/P9/P1) から独立に導いた結論」「利用者像から導いた結論」「原作者見解」の **3 経路が同じ結論に収束した**ことにある。「著者がそう言ったから従う」のではなく、独立した複数経路の一致が結論の強度を高めた。

## 10. 結論 (調査としての事実認定)

- 八百万の軽量入口の軽さは **検査範囲を絞ること (b)** が本質。記録の有無 (a) ではない
- 八百万に「合格だけ残す」思想は無い (P5 と一致)
- 部分追試は P3 (コード不変を前提にしない) と緊張し、未観測軸の劣化を見逃す。LLM 改修の周期では全観測コストが小さく省力化メリットも薄い
- 「部分検証」は実行時 verify でなく **REQ 分割 (設計)** で解く。各 REQ は全 stage を走らせるので P3 緊張が構造的に消える
- 思想憲章・利用者像・原作者見解の 3 経路が「verify (部分追試) は不要、毎回フルチェック」で一致
- よって qgb は `qgb verify` を採用しない。八百万の verify-req とはここで意図的に設計分岐する (むしろ八百万の本来思想に忠実であろうとすると verify は不要になる)

これを受けた spec 改訂 (受け入れ条件・CLI surface・各文書) は別途実施する。
